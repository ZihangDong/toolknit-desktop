# V3.3 一键记录模式快捷键冲突修复

日期：2026-10-28。V3.3 开发中，未发布。

## 已确认原因

用户反馈部分 Windows 电脑上自启动、剪贴板监控能单独开启，但一键记录模式和截图悬浮历史始终失败。排查发现：历史开关走 `quick_screenshot/configure`，旧实现每次都会注册保存的截图快捷键。启动时 Alt+Q 注册失败后，保存值仍为 Alt+Q，但实际注册为空；历史开关因此再次尝试注册并报冲突。

一键模式启用顺序是自启动、监控、历史。历史失败后撤回本次改动，回滚历史时又注册同一冲突键，于是出现“部分设置未能恢复”。前端仅展示通用提示，未保留具体失败阶段。用户随后实测更换截图快捷键，立即恢复正常，确认本次反馈的触发条件。

截图中的 CPU、GPU 和内存不是本次根因。其他智能体关于残留进程、辅助功能节点、单实例 panic 的推测不作为已证实原因。保存的全 false 快照表示开启前的恢复目标，不是实时状态；无需删除快照、历史数据、用户注册表项或 WebView2 数据来修复此问题。

## 修改边界

- `src-tauri/src/native_runtime/quick_screenshot/mod.rs`：历史开关不重试未改变的快捷键；失败恢复仅撤回本次确实执行的快捷键注册。偏好状态统一返回 shortcut/history/registered/error，历史保存成功不会抹掉现有快捷键冲突提示。
- 同一原生命令的 `configure` 请求新增可选 `updateShortcut` 布尔字段。快捷键值改变时仍照常注册；值未改变时，仅用户主动保存/重置/禁用传 true 才重试。不增加命令名或权限。
- `features/quick-screenshot/controller.js`：明确区分快捷键操作与历史开关。保留用户原快捷键，不自动抢占或替换组合。
- `app/recording-mode-state.js`：记录读设置、恢复快照、自启动、监控、历史、核验等失败阶段；仅返回受限产品错误代码。无设置改动时，读状态失败不再误报回滚失败。过期读取错误不覆盖后续成功状态。
- `app/recording-mode-runtime.js`：Toast 显示失败阶段与代码，调试控制台只记录安全摘要；状态读取失败可点击重试，仍未知时不执行任何修改。设置事件订阅失败不禁止手动操作。
- 中英文帮助与文案：说明冲突只影响快捷键，历史开关独立；说明快照用途和排查方式。

原有 `snapshot.v1`、提示关闭偏好、DOM ID、事件名、自动启动注册方式、剪贴板数据库与权限均保留。临时隐藏到下次重启保持原有语义，本次不重新定义记录模式聚合状态。

## 验证

原生测试覆盖历史开/关不调用冲突注册器、冲突状态继续显示、同键主动重试、修改组合、禁用和长度校验。状态测试覆盖原设置恢复、部分失败回滚、快照、重复点击、销毁、迟到读取与安全错误代码。浏览器专项覆盖白天/深色界面、失败步骤、读取失败后点击重试、监听失败后的正常操作，以及快捷键设置和历史开关的独立性。

- `test:recording-mode`、`test:quick-screenshot` 专项通过。

- `test:release` 110 项脚本通过，包含架构、构建、安全、CLI 独立包和 MCP 验证。
- 完整 Rust：265 passed、0 failed、12 ignored；新增 2 项原生快捷键/历史隔离测试通过。

浏览器故障注入使用模拟适配器；原生测试直接执行实际决策函数，未抢占系统快捷键。用户更改快捷键验证的是旧版绕过方式；修复代码尚需后续 Windows 测试包在反馈机器验收，本轮未修改本机真实自启动/监控设置或占用用户快捷键。未打包、提交或推送。
